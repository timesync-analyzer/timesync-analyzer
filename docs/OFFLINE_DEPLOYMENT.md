# Развёртывание без интернета

Инструкция разделяет подготовку выпуска на машине с интернетом и установку
готовых артефактов в изолированном контуре. На сервере не нужны Go, protoc,
PostgreSQL-клиент, sql-migrate, Python или установка пакетов приложения.
Нужны заранее установленные **Docker Engine и Docker Compose v2** с поддержкой
`pull_policy: never`, `service_completed_successfully` и `up --no-build --pull never`.
Если установка Docker тоже запрещена, его наличие должно входить в базовый образ ОС.

Предполагается, что агенты уже установлены на узлах. Их настройки описаны
в разделе 4.

## Состав серверной поставки

| Контейнер | Содержимое и назначение |
|---|---|
| `analyzer` | Приём метрик ZeroMQ, запись и расчёт метрик |
| `reportd` | HTTP API, ручные/автоматические отчёты, PDF/CSV |
| `migrate` | Создание ролей, расширения TimescaleDB и применение SQL-миграций |
| `timescaledb` | PostgreSQL 16 с TimescaleDB |
| `grafana` | Дашборды, datasource, alerting и плагины, уже включённые в образ |
| `grafana-renderer` | Рендеринг графиков для PDF |

`analyzer`, `reportd` и `migrate` используют один готовый образ приложения
с разными точками входа. Всего переносится четыре Docker-образа.
Мигратор ждёт готовности БД; analyzer, reportd и Grafana запускаются только после
успешных миграций. Хост выполняет только Docker-команды, SQL выполняется в контейнере.

Grafana не устанавливает плагины при старте. Проверки обновлений, телеметрия и
внешний SMTP в офлайн-конфигурации отключены. Webhook Grafana → reportd работает
внутри Docker-сети. Если нужны почтовые уведомления, отдельно настройте локальный SMTP.

## 1. Подготовить серверный комплект

На машине с интернетом, Docker и Buildx, из каталога `timesync-analyzer`:

```sh
git submodule update --init --recursive
sh scripts/build-offline.sh offline-1 ../delivery/server-offline-1
```

По умолчанию скрипт определяет архитектуру Docker-сервера автоматически.
Предполагается, что машина сборки и целевой сервер имеют одинаковую архитектуру.
Третий аргумент (`linux/amd64` или `linux/arm64`) нужен только для другой целевой
архитектуры; тогда требуется поддержка её сборки и запуска контейнеров.
Генерация protobuf и компиляция всех трёх Go-бинарников выполняются внутри сборки.
Локальный `config/.env` не попадает в образ или комплект.

Готовый каталог появляется только после успешной сборки. При ошибке временный
каталог удаляется, и команду можно повторить. Существующий комплект не перезаписывается.
Если после запуска старого скрипта остался пустой каталог, удалите его через
`rmdir ../delivery/server-offline-1` и повторите команду.

Содержимое комплекта:

```text
images.tar              все четыре образа
images.json             ID и метаданные образов
compose.yaml            запуск без build и скачивания образов
config.yaml             настройки analyzer и reportd
.env.example            имена пользователей и пустые поля секретов
form-panel.json         версия установленного плагина форм
infinity.json           версия установленного datasource-плагина
build-info.txt          версия выпуска, исходные образы и Git-ревизии
OFFLINE_DEPLOYMENT.md    эта инструкция
SHA256SUMS              контрольные суммы
```

По умолчанию исходные образы БД/Grafana/renderer и версии плагинов выбираются
на момент подготовки. Внутри выпуска все образы получают фиксированный тег выпуска.
Для повторяемой сборки задайте `TIMESCALE_IMAGE`, `GRAFANA_BASE_IMAGE`,
`RENDERER_IMAGE` с конкретными тегами или digest, а `FORM_PANEL_VERSION` и
`INFINITY_VERSION` — с конкретными версиями. Не меняйте major PostgreSQL
относительно существующей базы (этот рецепт использует PostgreSQL 16).
Храните принятый `images.tar`: повторный запуск сборки с плавающими источниками
может дать другой результат даже при том же имени выпуска.

Перед передачей комплект должен пройти приёмку на чистом сервере нужной
архитектуры с отключённым внешним доступом, включая генерацию PDF с графиками.

## 2. Установить сервер в изолированном контуре

Перенесите весь каталог, включая скрытый `.env.example`, например в
`/opt/timesync`. Далее команды выполняются из него, пользователем с доступом к Docker:

```sh
cd /opt/timesync
sha256sum -c SHA256SUMS
docker load -i images.tar
cp .env.example .env
chmod 600 .env
editor .env
```

Заполните все пустые пароли и токены разными случайными значениями.
Для `REPORT_TOKEN` используйте `report_` и случайные hex-символы после него:
`REPORT_TOKEN=report_<случайное_значение>`. Префикс обязателен для этого рецепта:
Grafana преобразует похожие на число переменные в числовой тип, из-за чего
webhook provisioning завершается ошибкой `authorization_credentials of type string`.
Кавычки вокруг переменной в YAML не предотвращают это преобразование.
Для текущей строки подключения приложения используйте пароли в hex
(например, 64 случайных шестнадцатеричных символа), без пробелов, `$`, кавычек
и URL-разделителей. Подготовьте их на сборочной машине или существующим
генератором паролей; установка генератора на сервере не требуется.
Имена APP_USER, ADMIN_USER и READONLY_USER должны различаться между собой,
с POSTGRES_USER и с групповыми ролями timesync_app/timesync_admin/timesync_user.

`config.yaml` содержит размеры очередей, интервалы, настройки reportd, очистки
и автоматических отчётов. Параметры подключения, учётные данные и REPORT_TOKEN
поступают из `.env`. Пароли существующей БД и Grafana при перезапуске не меняются
от редактирования `.env`; сохраняйте их при обновлении.

```sh
docker compose config --quiet
docker compose up -d --no-build --pull never
docker compose ps -a
docker compose logs --tail=100 migrate analyzer reportd
```

Для `migrate` нормален статус **Exited (0)**. Остальные пять контейнеров должны
работать. Отсутствующий образ вызывает ошибку, а не загрузку из интернета.
При ошибке миграции не запускайте сервисы с `--no-deps` и не удаляйте volume:
исправьте причину по логам и повторите `docker compose up`.
Проверка применённых миграций также выполняется в контейнере:

```sh
docker compose run --rm --no-deps migrate status
```

Открываемые порты: TCP 10000 для агентов, TCP 3000 для Grafana, TCP 8080 для
API reportd. PostgreSQL и renderer наружу не публикуются. Разрешите эти порты
между нужными узлами локальной сети. TLS в этом комплекте не настраивается.

## 3. Проверить сервис отчётов и метрики

1. Откройте `http://<сервер>:3000` и войдите с GRAFANA_ADMIN_USER/PASSWORD.
2. Убедитесь, что datasource TimescaleDB и ReportD доступны, а дашборды установлены.
3. После запуска агентов проверьте появление узлов и свежих метрик.
4. Откройте дашборд управления отчётами, запросите отчёт по периоду с данными.
   Дождитесь завершения и скачайте PDF/CSV. В PDF должны быть графики.
5. При ошибке смотрите `docker compose logs --tail=100 reportd grafana grafana-renderer`.

Для быстрой проверки HTTP откройте `http://<сервер>:8080/healthz`.
Ответ healthz подтверждает работу HTTP-сервиса, но не заменяет проверку БД и PDF.
Для API `/api/reports` нужен заголовок `Authorization: Bearer <REPORT_TOKEN>`.
В Grafana токен подставляется через provisioning datasource/webhook.
Файлы отчётов сохраняются в volume `reports_data`, БД — `timescaledb_data`,
настройки Grafana — `grafana_data`. Временная очередь reportd хранится в памяти:
перед обновлением дождитесь завершения нужных заданий.

## 4. Настроить агентов

На каждом узле измените `/etc/time-agent/config.yaml`:

| Параметр | Что указать |
|---|---|
| `global.node` | Уникальное имя узла, которое будет отображаться на сервере |
| `zmq.endpoint` | `tcp://<IP_сервера>:10000`; если порт сервера изменён, укажите его |
| `temperature.sensors[].name` | Имена температурных датчиков данного узла |
| `services.ptp4l.on`, `services.phc2sys.on` | Включите сбор только используемых источников; для чтения журналов оставьте `source: journal` |
| `ptp_topology.on` | Включите, если требуется сбор PTP-топологии |
| `ptp_topology.pmc_path` | Путь к установленному `pmc`, по умолчанию `/usr/sbin/pmc` |
| `ptp_topology.uds_path` | Путь к управляющему сокету локального ptp4l |
| `ptp_topology.domain_number` | Номер домена, совпадающий с `domainNumber` в конфигурации ptp4l |
| `services.ppswatch.on` | `true`, если используется PPS; иначе `false` |
| `services.ppswatch.dev` | Путь к PPS-устройству, например `/dev/pps0` |
| `services.ppswatch.executable_path` | Путь к установленному `ppswatch`, если он отличается от `/usr/bin/ppswatch` |

Для ppswatch сохраните `source: "subproccess"` — именно это значение ожидает
текущий парсер. Если `executable_path` не задан, используется `/usr/bin/ppswatch`.

## 5. Обновление и резервная копия сервера

Сохраняйте имя Compose-проекта: для новой установки это `timesync`.
При переходе со старого `docker-compose.yaml` сначала определите старое имя
через `docker compose ls` и используйте его с `-p <старое_имя>` во **всех**
командах нового комплекта. Иначе Compose создаст другие volumes и база будет выглядеть пустой.
Проверьте существующую таблицу учёта миграций: рецепт использует
`public.gorp_migrations` с именами SQL-файлов. Если схема ранее создавалась вручную
или другим мигратором, сначала согласуйте историю на копии БД; автоматического
присвоения версии существующей схеме здесь нет.

До остановки дождитесь завершения отчётов, при необходимости остановите агентов.
Ниже пример холодной копии для проекта `timesync`; подставьте фактические имена
volumes и тег старого образа. Не выполняйте `down -v` — он удаляет данные.

```sh
mkdir -p backup
cp .env config.yaml compose.yaml backup/
chmod 700 backup
docker compose down
docker volume inspect timesync_timescaledb_data timesync_grafana_data timesync_reports_data
for volume in timesync_timescaledb_data timesync_grafana_data timesync_reports_data; do
  docker run --rm --pull never --user 0 --entrypoint tar \
    -v "$volume:/source:ro" -v "$PWD/backup:/backup" \
    timesync-analyzer:offline-1 -czf "/backup/$volume.tar.gz" -C /source .
done
```

Храните резервную копию вместе со старым комплектом образов и конфигурацией.
После успешной копии загрузите новый `images.tar`, проверьте SHA256SUMS **в новом
комплекте до редактирования файлов**, замените compose.yaml и обновите RELEASE в
существующем `.env`, сохранив пароли. Изменения config.yaml перенесите осознанно.

```sh
docker load -i /путь/к/новому/images.tar
docker compose config --quiet
docker compose up -d --no-build --pull never
docker compose logs --tail=100 migrate analyzer reportd
```

После `down` контейнер миграций создаётся заново и применяет только ещё не
выполненные миграции. Перезапуск уже развёрнутого выпуска не применяет их повторно.
Не запускайте несколько миграторов одновременно для одной БД.

При откате сначала остановите новый стек. Восстанавливайте **все три** volumes
из холодной копии, старые конфигурацию и образы: простой возврат тега не отменяет
изменения схемы. Восстановление перезаписывает данные и выполняется только для
явно выбранных volumes; не распаковывайте копию поверх работающей БД.
Для возврата без удаления новых данных можно создать отдельные volumes,
распаковать туда архивы через тот же образ с `tar -xzf`, затем указать их
через `name:` у volumes в старом compose-файле.

## Что проверить перед выпуском

- Чистая установка без сети: миграции прошли, агенты присылают метрики, PDF содержит графики.
- Повторный запуск: миграции не дублируются, данные и отчёты сохранены.
- Обновление на копии реальной БД и пробное восстановление резервной копии.
- Отсутствие библиотек `not found` на агенте, работа всех нужных источников метрик.

Проверка синтаксиса Compose не подтверждает совместимость конкретных версий
TimescaleDB, Grafana и плагинов. Полную приёмку выполняйте для каждого комплекта.
